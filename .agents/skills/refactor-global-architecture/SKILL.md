# Глобальний рефакторинг архітектури

## Швидка активація (для запитів будь-якою мовою)
- **Використовувати, коли**: треба змінювати архітектурні межі, контракти, залежності або структуру модулів.
- **RU сигнали**: сделай глобальный рефакторинг, архитектурный рефакторинг, реорганизуй модули
- **EN signals**: global architecture refactor, cross-module refactor, restructure architecture
- **Не використовувати, коли**: достатньо локального non-breaking рефакторингу (refactor-safe-local).

## Обовʼязковий процес
1. **Фіксація цілей**: що саме покращуємо (звʼязність, тестованість, підтримуваність, продуктивність).
2. **Scope та ризики**: які модулі, контракти, API, міграції БД, інтеграції зачіпаються.
3. **План по кроках**: малі ітерації, кожна з перевіркою сумісності.
4. **Backward compatibility**: де потрібно — адаптери, deprecated-шар, поетапне перемикання.
5. **Валідація**: тести/стат-аналіз/ручні перевірки критичних сценаріїв.
6. **Стандарти**: додатково орієнтуйся на скіл `coding-standards-always`.
7. **Цільова архітектура** (тільки якщо рефакторинг явно ведеться "під нову архітектуру"): скіли
   `laravel-architecture`/`laravel-actions`/`laravel-dtos`/`laravel-query-builders` та інші з
   родини `laravel-*` (джерело: `leeovery/agentic-skills`). Без явного запиту на нову архітектуру
   рефакторинг лишається в межах поточної (Service/Action-класи, як є).

## Що відрізняє від простого рефакторингу
- `refactor-safe-local`: без зміни архітектурних контрактів.
- `refactor-global-architecture`: **дозволяє** зміну архітектури, але лише за узгодженим планом і контрольованим ризиком.

## Вихідний формат для кожної ітерації
- Що змінено.
- Які ризики закрито.
- Що ще лишилось.
- Які перевірки пройдено.

## Важливі нюанси
1. Без чіткого scope не стартувати.
2. Не змішувати з feature-розробкою в одному PR/таску.
3. Підтримувати міграційний шлях для старих викликів, якщо це критично.
4. Заборонено змінювати бізнес-логіку
